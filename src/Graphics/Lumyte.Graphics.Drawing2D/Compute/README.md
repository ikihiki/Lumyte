# GPU tiled execution

ComputeExecutionPlan2D encodes raw curve controls, immutable paint records and CPU-normalized clip membership. ComputeGeometryPlan2D uses binary64 second-difference bounds for fills and a certified logical-tangent bound for strokes, with fixed subdivision reservations; it does not expand edges on CPU.

For the current shader (logical centerline chord normals), regular curve stroke bodies with bevel joins and butt caps use `E(N) <= D/(8N²) + S*w*M/(2*m*N)`, where D bounds transformed acceleration, M bounds logical acceleration, S is the affine Frobenius norm, w is half-width and m is a strictly positive speed lower bound certified by an outward-rounded separating-direction dot product over derivative controls. Required subdivisions satisfy E<=0.125; capacity excess rejects rather than clamps. Exact binary32 integer predicates allow collapsed curves and constant nonnegative derivative rays (including zero controls); other uncertifiable derivative hulls reject before raw-array allocation. Fill subdivision remains unchanged. The geometric theorem is specifically BODY+BEVEL+BUTT, not an assertion about square-cap tips, miter tips or round tessellation; those styles keep their existing functional tests and round reservation rules. This is an exact-arithmetic geometric approximation theorem, not a global 0.125-pixel guarantee for float32 GPU output. Float32 point evaluation, short-chord subtraction, normalization and final transformation error are not included. In particular, a large logical origin can quantize short chords despite passing the device hull guard. Native fixture readbacks qualify the tested coordinate ranges only; a general GPU rounding bound remains unproved.

ComputeExecution2D owns upload and writable frame-private storage. Eleven explicit dispatches initialize, generate curves, expand strokes, count/scan/fill tile references, propagate backdrop sample rows, count/scan/fill ascending draw candidates, and shade. Output is float32 premultiplied color; each draw is averaged over the correlated 4x4 grid before scene SrcOver. Ordinary graphics resolve uses SrcOver into the caller attachment, preserving Load background. No storage textures or submit/wait are required.

The baseline implementation uses serial per-draw stroke expansion and serial prefix scans. This is functional algorithm separation, not a performance claim. Inputs outside checked curve, geometry, tile reference, binding, logical-coordinate and working-byte reservations fail explicitly. Seven physical storage buffers are required for compute: records, combined paint/clip directory, masks, images, combined curve/numeric input, writable storage and writable work. Resolve has a separate read-only table. Unsupported device limits reject explicitly, without another renderer fallback.

The graph adapter registers batch-owned prepared buffers as non-observable multi-pass preparation resources. This differs from single-pass-confined UseLocalBuffer: dependencies and uninitialized reads are checked across stages, and unused image producers are culled. Owners survive renderer disposal until graph plan retirement.

Retained frames reuse completed exclusive assets and renderer-local CPU geometry plans. A general standalone cross-frame CPU paint-program cache is not implemented. Test coverage and GPU validation must be reported separately from encoding/ABI tests; shader compilation alone is not image proof.
