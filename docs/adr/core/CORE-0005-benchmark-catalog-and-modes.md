# ADR-CORE-0005: Coreの測定ケースを先に定義し、実行モードを分離する

- 状態: 提案
- 日付: 2026-11-14
- 基準コミット: `05d391955a607e7fb948812c9660dc2bed32704d`

## 背景

Coreを変更する開発者は、短時間の退行検知に適する処理だけを先に選ぶと、初期構築、競合、資源の寿命、生成器などの重要な経路が測定対象から消える。基準コードの[固定ケース選択](https://github.com/ikihiki/Lumyte/blob/05d391955a607e7fb948812c9660dc2bed32704d/build/ComponentScreeningData.cs)はSignalsの12ケースを扱い、[数値ベンチマーク](https://github.com/ikihiki/Lumyte/blob/05d391955a607e7fb948812c9660dc2bed32704d/benchmarks/Core/Lumyte.Mathematics.Benchmark/Program.cs)は独立した計時処理を持つため、Core全体の測定範囲と実行条件を同じ基準で説明できない。

## 決定

Coreの全プロジェクトについて、意味の異なる処理経路をケース群として先に定義し、その後に確認・スクリーニング・正式比較・診断の実行モードを選ぶ。ケースの目的と正当性をモードから独立させることで、実行時間を短くする際も測っていない範囲を残せる。

### 利用者の変更前・変更後

利用者はCoreの実装を変更し、どの処理の性能を確認するか判断する開発者である。

| 操作 | 基準コードでの手順 | 提案する手順 |
| --- | --- | --- |
| 測定対象を確認する | 固定Signalsケース、数値計時、個別sampleの処理を調べる | Coreのケース群を処理境界・入力・正当性・寿命条件で一覧化する |
| 短時間で変更を確認する | 固定カタログへ該当するか、未対応の変更かを判定する | カタログから変更依存先と短縮可能な具体ケースを選び、未選択範囲を記録する |
| 初回生成や競合を調べる | 短時間のCPU処理と同じ測定として扱う危険がある | 初回・定常、単一所有者・競合、生成時・実行時を区別したケースで比較する |
| 原因を調べる | 通常の計時に診断処理を足す | 同じ入力契約を診断モードで再実行し、比較の計時結果とは別に保存する |

上記は提案する運用であり、基準コードにCore全体のモード選択機能があるとは扱わない。[既存のFallout入口](https://github.com/ikihiki/Lumyte/blob/05d391955a607e7fb948812c9660dc2bed32704d/build/Build.ComponentScreening.cs)とSignalsの通常測定・短縮測定を、本決定だけで変更済みにはしない。製品ライブラリの公開API、所有権、例外、依存方向は変更しないため、公開API宣言の差分はない。

### カタログの単位と網羅範囲

対象は基準コミットのsrc/Core以下の17プロジェクトである。数学、時刻、メモリ、編集、Signals、Resources、Settings、Execution、Composition、状態機械、Worldsを扱い、依存注入・埋め込み資源・実行アダプター・生成器も分類から落とさない。

ケース群は、意味の異なる算法、状態遷移、再利用、保持・解放、失敗経路をまとめた測定契約である。全てのメソッド名の別名、型、入力値の直積を測定する意味ではない。各プロジェクトは、独立して測る、利用側に含めて測る、生成時に測る、正しさだけを検査する、のいずれかと理由を持つ。経路を実行できない場合は不適合とし、別の軽い処理で代用しない。

各ケース群は安定した識別子を持ち、境界・入力・正当性を変えた場合は版を更新する。具体ケースの識別子には入力プロファイル、数値型、所有者・競合条件、初回・定常条件を含める。空入力、同値代入、cache hitなどの対照は意図して識別し、実際の更新処理と同じ結果に集約しない。

### 必須の測定契約

ケースごとに、次の事項を確定してから計時する。

- 目的、実在する公開入口または承認されたアクセス経路、対象ソースとケースの版。
- 1操作の開始・終了境界と、結果を消費する方法。非同期ではenqueueの完了と処理の完了を別のケースにする。
- 代表値・境界値・負荷値の入力プロファイル。例外や拒否を扱うなら成功経路とは別の識別子にする。
- 構築、入力更新、再利用、reset、cleanupの扱い。毎回無限に履歴や作業集合が増えない条件を示す。
- 結果、identity、順序、revision、操作回数、解放責任などの正当性確認。既存の決定的テストを参照し、計時値を単体テストのassertへ持ち込まない。
- 実行時間、managed割り当て、保持量、仕事量の指標と単位。保持量は専用checkpointで測り、割り当て量と同一視しない。
- 対応OS、SDK、runtime、CPU機能、外部資産、実I/O、thread配置などの条件。初回コンパイルやOS cacheが不明な場合は不明と記録する。

内部メンバーや既存テストのfriend accessを、新しいベンチマークから自動的に利用できるとは仮定しない。必要なアクセス変更は別途明示する。資源・メモリの回収を速く見せるために、[実行の所有権](CORE-0003-execution-and-jobs.md#決定)や[Worldの進行順](CORE-0002-world-stack.md#決定)を省略しない。

### 実行モード

| モード | 目的 | 観測と判定 |
| --- | --- | --- |
| 確認 verify | ケースの入口、入力、正当性、寿命を最小プロファイルで確認する | 動作確認のみ。短い実行の時間から性能を判定しない |
| スクリーニング screen | 選択した代表条件で退行候補を見つける | 固定した短縮設定で比較する。候補・候補なし・判定保留・不適合・未実行を分ける |
| 正式比較 compare | 宣言した入力条件の差とばらつきを確認する | 独立プロセスの繰り返し、A/A対照、交互の比較順と生データを保存する |
| 診断 diagnose | 計時差を生む工程、割り当て、仕事量を調べる | trace・counter等を取得する。診断実行の時間を正式比較値として使わない |

モードは測定対象そのものを変更しない。同じケースの軽い入力と重い入力は別の具体ケースとして識別し、重い入力を黙って軽い入力へ置換しない。生成器や実threadの競合など、短い測定では意味を保てない経路はスクリーニング不適合でもカタログに残す。

各ケース群にはモードの適性と理由を記載するが、PRごとの対象、定期実行の頻度、実行予算、固定の閾値、正式比較の反復数の最終割り当ては、この段階で一律に確定しない。カタログを確認してから、実測した所要時間とノイズに基づいて選ぶ。モードを理由に既存の正当性検査やdeadlineを緩めない。

### モードから独立させる軸

- 頻度: PR、定期、手動。正式比較が定期実行であるとも、PRが常にスクリーニングであるとも固定しない。
- 測定段階: 初回プロセス、初回オブジェクト、定常、容量境界、再訪・回収、競合。異なる段階を合算しない。
- 環境: 単一threadの純粋CPU、協調実行、実thread、実I/O、生成時処理。mockの待ち時間を実I/Oや実threadの測定とは呼ばない。
- 仕事量: 要素数、更新率、依存グラフ、文字種、数値型など。全パラメーターの直積を必須にせず、各経路を区別する最小プロファイルを宣言する。

### 既存ケースの統合

既存の対象別ベンチマークをカタログへ先に対応付け、同じ処理とoracleをコピーした新しいケースを増やさない。Signalsの配送・依存・再利用・scheduler・async・保持量、Mathematicsの変換bounds・距離span、Execution sampleの配送対照は、処理境界と寿命を確認して再利用する。独自ループや旧runtime設定は入力契約と分けて扱い、過去の方式の対照や保存済み測定値を現在の製品baselineにはしない。

Coreに依存するだけのUI・Graphicsハーネスは測定主体のカテゴリへ残す。統合時に同義のケースをまとめる場合も、元のケースと新しい識別子の対応、残す入力・仕事量・正当性を記録する。実装・比較証拠の再確認を終える前に、移植済みや性能同等とは扱わない。

### 実行基盤と結果

コードはテストと同じカテゴリ構成のbenchmarks/Core/<対象project>.Benchmarkへ置き、比較対象の両SHAには同じ版のハーネスを適用する。選択、構築、実行、解析、結果保存、通知は既存FalloutのC# runnerへ集約し、Pythonや独立した計時スクリプトを追加しない。

managed CPU計時は既存のBenchmarkDotNetを再利用する。正式比較に十分な設定はケース単位で固定し、[Signalsの現行設定](https://github.com/ikihiki/Lumyte/blob/05d391955a607e7fb948812c9660dc2bed32704d/benchmarks/Core/Lumyte.Signals.Benchmark/Program.cs)を名前だけで正式比較に昇格しない。生成器はRoslyn driverなど実際の生成経路を使用し、生成済みコードの実行とは分離する。診断はruntime標準の取得手段を優先し、計時と別実行にする。

同じhost・SDK/runtime・ハーネス・入力契約で比較し、製品の既定JIT・PGO・GCを維持する。計時中に同じhostで別のbuild・test・性能測定を並行しない。非同期の割り当てをcurrent-thread値だけで総量と断定せず、把握できない指標は欠損として残す。

各実行はケース識別子と版、両SHA、ソース・ハーネス・実行ファイルのhash、モード、入力、環境、実効job設定、正当性結果、生データと不適合理由を保持する。BenchmarkDotNetのiteration推定値の分位点を個別フレームや要求の遅延分位点と呼ばない。timeout、欠損、比較不能、未選択を「退行なし」にしない。キャンセル時も完了済みの証拠を保存し、未知の子プロセスや資源を残さない。

### 受け入れ条件

- Coreの全17プロジェクトがケース群または利用側統合・生成時・正当性専用の理由へ対応する。
- 各ケース群の目的、1操作、入力、reset、oracle、対応環境、モード適性が一意に読める。
- 初回・定常、cache hit・更新、実処理・拒否、生成時・実行時を同じ比較結果に混ぜない。
- ケースの網羅と実行選択を分離し、短時間枠で未選択のケースを追跡できる。
- 本設計の合意や文書検査は、実装の存在、性能改善、測定ノイズの校正の証拠とは扱わない。

## 検討した代替案

- スクリーニングに向く処理だけを選ぶ: 導入は軽いが、初期構築・回収・競合・生成時処理が測定範囲から消える。カタログを先に定義する。
- 全メソッドと全入力の直積を毎回測る: 名称上は網羅できるが、同じ意味のaliasや巨大な組合せが実行時間を占める。意味の異なる経路と代表・境界・負荷プロファイルで網羅する。
- 各プロジェクトに独立したrunnerを追加する: ローカルの実験は容易だが、選択・比較・失敗・証拠保存の契約が分岐する。対象別projectと共通Falloutを組み合わせる。
- 短縮・正式・診断のケースを別々に実装する: 最適な計時を選べる一方で入力・仕事量・oracleが乖離する。同じケース契約にモードとプロファイルを割り当てる。

## 結果と影響

開発者はCore全体で何を測り、何を測っていないかを確認してから、実行時間と精度の予算を配分できる。プロジェクトごとの無条件なケース数ノルマは設けず、薄いアダプターや契約型は利用側の測定へ帰属させる。

ケースの版、正当性、resetと所有権、環境条件の保守が必要になる。頻度・閾値・予算・正式比較の反復設定はカタログ完成後の選択事項であり、未測定の速度や全Coreの退行検知を保証しない。製品APIと既存ADRの判断本文は維持する。
