# ADR-0001: ADR の書き方と運用

- 状態: 採用
- 日付: 2026-10-05

## 背景

Lumyte は設計判断を ADR（Architecture Decision Record）に記録してから実装する。実装だけでは残りにくい判断の背景、採用理由、代替案、影響を共有し、後から設計を見直せるようにするため、記述形式と運用ルールを定める。

## 決定

### 配置と命名

- ADR は `docs/adr/<category>/` に Markdown で配置し、日本語で記述する。
- カテゴリのディレクトリ名は英語の小文字とハイフン、カテゴリコードはその名前を大文字にしたものとする。例: `input` と `INPUT`、`graphics` と `GRAPHICS`。
- ファイル名は `CATEGORY-NNNN-short-description.md`、タイトルは `ADR-CATEGORY-NNNN: 設計判断の題名` とする。説明部分は英語の小文字とハイフンを使用する。
- 一つの ADR は一つの主要な設計判断を扱う。密接に関係する事項は同じ ADR に含めてよい。
- リポジトリ全体の運用や構成は `governance`、入力システムは `input`、その他の機能は主たる責務のカテゴリに配置する。複数カテゴリにまたがる判断は主カテゴリに一度だけ記録し、関連 ADR からリンクする。
- カテゴリは `src/` の機能分類を参考にするが、一対一の対応は必須としない。新しいカテゴリは既存カテゴリと責務が重複しない名前で追加する。

### カテゴリ別の採番

- ADR の識別子はカテゴリコードとカテゴリ内連番の組み合わせとする。番号は各カテゴリで `0001` から独立して採番し、全カテゴリ共通の連番は使用しない。
- 例えば `INPUT-0001` と `GRAPHICS-0001` は異なる識別子であり、別カテゴリで作業中の ADR や予約番号を待たずに採番できる。
- 同じカテゴリ内では、main の ADR と作業中の PR・番号予約を確認し、使用済み・予約済みの最大番号の次を割り当てる。並行作業では共通の Issue などでカテゴリ、番号、担当 PR を予約し、同じ番号を使用しない。偶発的な重複は後から予約した側が main への取り込み前に解消し、関連リンクも更新する。
- 番号は実装順や優先順位を表さない。予約済み・使用済みの番号は再利用せず、統合や削除による欠番を許容する。main に取り込まれた識別子は変更しない。
- ADR 同士の参照は相対リンクを使用し、番号だけでなくカテゴリを含む識別子または題名で示す。カテゴリを見直す場合も、main に取り込まれた ADR の識別子とパスは維持し、関連カテゴリを本文に追記する。

### 既存 ADR の扱い

このルールを導入する前の `docs/adr/NNNN-short-description.md` と `ADR-NNNN` は、既存の識別子とリンクを維持するためそのまま残す。既存の `ADR-0001`、`ADR-0002`、`ADR-0003` はリポジトリ全体の運用・構成に関する文書として扱うが、新形式のカテゴリ内連番には含めない。新規 ADR からカテゴリ別の配置と採番を適用する。

入力システムの最初の ADR は、他カテゴリや既存 ADR の番号に関係なく `docs/adr/input/INPUT-0001-input-system.md`、タイトルは `ADR-INPUT-0001: Input システムの設計` とする。

### 記述内容

各 ADR に次の項目を記載する。

| 項目 | 内容 |
| --- | --- |
| 状態 | 提案、採用、却下、廃止、置換済みのいずれか |
| 日付 | ADR を作成した日付。`YYYY-MM-DD` 形式 |
| 背景 | 解決する問題、要求、制約、判断が必要な理由 |
| 決定 | 採用する方針と、その適用範囲 |
| 検討した代替案 | 比較した選択肢と、採用しなかった理由 |
| 結果と影響 | 利点、欠点、制約、実装や運用への影響 |

必要に応じて「別途決定する事項」や参考資料を追加する。関連 ADR は相対リンクで参照する。決定済みの事項と未決定の事項を区別し、仮定を確定事項として記述しない。

文章は、会話の経緯を知らない読者にも判断を理解できるように書く。コードや図は判断の説明に必要な範囲で使用し、詳細な実装手順は別のドキュメントで管理する。

### 設計対象に応じて選択する項目

必須項目に加え、以下から設計判断を説明するために必要な項目を選ぶ。すべてを機械的に埋める必要はない。各項目は「決定」の小見出し、または独立した節として記述してよい。

| 項目 | 選択する場面 | 記述する内容 |
| --- | --- | --- |
| 目的と非目標 | 対象範囲が広い設計 | 実現すること、今回扱わないこと |
| ユースケース | 利用方法が設計に影響する場合 | 想定する利用者、代表的な操作と利用例 |
| 公開 API 一覧 | ライブラリやモジュールの公開境界を設計する場合 | 名前空間、公開型、主要メンバー、シグネチャ、役割 |
| API の契約 | 呼び出し側が守る条件や保証がある場合 | 入出力、事前条件、事後条件、例外、失敗時の振る舞い |
| 責務と依存関係 | 複数のプロジェクトや層に関わる場合 | 各構成要素の責務、依存方向、境界 |
| データモデル | データ表現を決める場合 | 型、構造、識別子、不変条件、シリアライズ形式 |
| 処理フローと状態遷移 | 手順や状態で動作が変わる場合 | 初期化、更新、終了、状態遷移、呼び出し順序 |
| 所有権とライフサイクル | リソースを生成・共有・破棄する場合 | 所有者、有効期間、解放責任、破棄後の扱い |
| スレッドと非同期処理 | 並列処理や非同期 API を扱う場合 | 呼び出せるスレッド、同期、キャンセル、完了条件 |
| エラー処理 | 失敗を利用側へ伝える場合 | 例外、結果型、エラーコード、復旧方針 |
| Native 相互運用 | C# と C++ の境界を設計する場合 | C ABI、型対応、マーシャリング、メモリとエラーの受け渡し |
| プラットフォーム対応 | OS や描画 API で差がある場合 | 対応表、必要な機能、未対応時の振る舞い |
| パッケージとビルド | 配布や参照方法を決める場合 | NuGet 名、依存、RID、成果物、ビルドと復元の方針 |
| 性能とリソース制約 | 性能が判断基準になる場合 | 目標、測定条件、割り当て、メモリ使用量、許容するトレードオフ |
| 互換性と移行 | 既存の契約やデータを変更する場合 | 破壊的変更、バージョニング、移行方法 |
| 検証方針 | 判断の成立を確認する場合 | 確認する振る舞い、受け入れ条件、必要なテストや測定 |
| 別途決定する事項 | 判断を分割する場合 | 未決定事項、後続 ADR の対象 |
| 参考資料 | 外部仕様や関連判断を根拠とする場合 | 関連 ADR、公式仕様、調査結果へのリンク |

### ライブラリの公開 API 一覧

ライブラリの設計 ADR には、原則として対象範囲の公開 API 一覧を含める。既存ライブラリの一部を変更する ADR では、追加・変更・廃止する API と関連する契約に絞る。

型名だけでなく、利用側が実装を参照せずに使い方を判断できるよう、主要なコンストラクター、メソッド、プロパティ、イベントとその役割を示す。オーバーロードや型制約が判断に影響する場合は、そのシグネチャも明記する。

```markdown
| 公開 API | 役割 | 契約・注意事項 |
| --- | --- | --- |
| `名前空間.型名` | 型の責務 | 所有権、利用可能な環境など |
| `戻り値 型名.メソッド名(引数)` | 操作の役割 | 事前条件、失敗、スレッド制約など |
```

必要に応じて C# 宣言や C ABI 宣言、短い利用例を併記する。公開 API の仕様を別文書にまとめる場合は、その文書へ相対リンクを張り、ADR 側には判断の対象となる API と採用理由を残す。実装後の網羅的な API リファレンスは別途管理し、ADR はその判断時点の設計を記録する。

### 状態と実装

- **提案**: 検討中で、まだ合意されていない判断。
- **採用**: 合意され、実装の方針として使用する判断。
- **却下**: 検討したが採用しなかった判断。
- **廃止**: 適用を終了し、後継の判断がないもの。
- **置換済み**: 新しい ADR によって置き換えられた判断。

設計に関わる実装は、対応する ADR を記述し、採用してから進める。会話やレビューで合意済みの判断は、最初から「採用」として記録してよい。「採用」は設計への合意を表し、実装や検証の完了を意味しない。

### 変更と履歴

ADR 自体が main に取り込まれるまでは、「採用」の状態でも設計判断を含めて同じ ADR を編集できる。レビューや実装中の見直しはその ADR に反映し、変更前の案を残すためだけに後継 ADR を作らない。main に入る前の ADR 同士の統合や、不要になった ADR の削除も可能とする。

main に取り込まれた ADR の設計判断を変更する場合は新しい ADR を作成し、旧 ADR を「置換済み」にして変更日、理由、後継へのリンクを追記する。新 ADR にも置換元へのリンクを記載する。誤字修正、判断の意味を変えない説明の補足、既存のルールに沿った具体化は、main への取り込み後も既存 ADR に反映できる。

「採用」は設計への合意を表し、main への取り込みとは区別する。取り込み状況は Git の main または origin/main の履歴で確認する。main に取り込まれた ADR は、却下、廃止、置換済みでも削除せず、判断の履歴として保持する。状態変更時には変更日と理由を追記する。

### 記述テンプレート

新しい ADR は以下を基本形とする。代替案がない場合も、その理由を記述する。

```markdown
# ADR-CATEGORY-NNNN: 設計判断の題名

- 状態: 提案
- 日付: YYYY-MM-DD

## 背景

解決する問題と制約。

## 決定

採用する方針と適用範囲。

## 検討した代替案

比較した選択肢と採用しなかった理由。

## 結果と影響

利点、欠点、制約、実装や運用への影響。
```

## 検討した代替案

### 全カテゴリ共通の連番を使用する

別カテゴリの並行作業でも番号の調整が必要になり、採番の衝突が起きる。カテゴリコードとカテゴリ内連番を組み合わせ、採番の調整範囲を同じカテゴリ内に限定する。

### README やコードコメントだけで設計を説明する

利用方法や局所的な実装の説明には適しているが、設計判断の背景と変更履歴が分散するため、ADR を独立した文書として管理する。

### 一つの大きな設計文書にまとめる

全体像を示しやすい一方、個々の判断の状態や置換関係を追いにくい。主要な判断ごとに ADR を作成し、関連する文書をリンクする。

## 結果と影響

- 設計を実装前に確認でき、採用理由と変更履歴が残る。
- 別カテゴリは独立して ADR を追加できる。同じカテゴリ内の並行作業では番号予約と重複確認が必要になる。
- 既存 ADR のパスを維持するため、旧形式とカテゴリ別の新形式が共存する。
- 設計を変更する際は、コード変更に加えて ADR の作成や状態更新が必要になる。
- 設計判断を伴わない局所的な修正まで ADR を必須とせず、記録の対象を主要な設計判断に絞る。
