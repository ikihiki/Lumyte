# ADR-0001: ADR の書き方と運用

- 状態: 採用
- 日付: 2026-10-05
- 更新日: 2026-11-02（参照範囲、利用者の変更前後、文章構成を改定）
- 基準コミット: `fbc81051cbf0f4aa5d996237543765e02b8cfa5c`（今回の改定の参照基準）

## 背景

ADR の読者は、変更の必要性を判断し、自分のコードや手順をどう変えるか理解する必要がある。他の作業の経緯、未定義の内部用語、長い API 一覧から説明を始めると、何を解決する判断なのかを読み取れない。

設計判断を実装前に記録する方針を維持し、判断時点の事実、採用理由、利用者への変化を短く説明する書き方を定める。

## 決定

ADR は、過去の ADR と判断時点のソースコードを根拠に、利用者の困りごとと変更前後を先に説明する。設計の詳細は、その判断を理解するために必要な範囲へ絞る。本 ADR を作成・更新ルールの正本とする。

### 利用者の変更前・変更後

このルールの利用者は ADR の作成者とレビュー担当者である。

| 作業 | 変更前 | 変更後 |
| --- | --- | --- |
| 判断を説明する | 方針と API 一覧を中心に書き、利用例は必要に応じて追加する | 利用者の困りごとと同じ操作の変更前後を書いてから、理由と API 差分を示す |
| 根拠を示す | 関連資料や作業経緯も本文に含められる | 基準コミットを固定し、その時点の ADR とソースだけを参照する |
| 既存判断を変更する | 旧 ADR にも後継への説明を追記する | 新 ADR に変更元と変更範囲を記録し、旧 ADR の判断本文は保持する |
| 文書を検査する | 一般的な Markdown の書式と目視で確認する | 新規・編集した ADR の構造と参照も Markdown lint で検査し、意味の整合性はレビューする |

作成者には変更前の事実と利用例を確認する作業が増える。読者は、別の作業の経緯や API 一覧を読み解く前に、自分への影響を判断できる。

### 参照できる範囲

- 各 ADR の冒頭に、判断の前提とした main の固定コミット SHA を「基準コミット」として記載する。一意な短縮 SHA は使用できる。番号や作成日の大小だけで ADR の前後を判定しない。
- 言及・参照できる既存資料は、基準コミットに存在する過去の ADR とソースコード（設定・テストを含む）だけとする。過去 ADR の判断を前提にする場合は、基準時点の状態と有効な範囲を確認する。
- 過去 ADR は相対リンクと対象節で示す。ソースコードは基準コミットの SHA とリポジトリ内パス・型・メンバーを示す。リンクを付ける場合も、ブランチ名ではなく SHA で固定する。
- PR、Issue、会話、レビュー経緯、並行作業、将来の ADR・実装予定、外部資料、別の設計文書・測定レポートを本文の前提や参照先にしない。番号やリンクを消して「別の作業」と言い換えることも避ける。必要な事実を、許可された根拠から説明し直す。
- 調査・採番調整には他の資料や作業情報を使用できるが、その経緯は ADR に持ち込まない。今回提案する設計と変更後の利用例は本 ADR 自身で説明し、既存実装と区別する。
- 対象外は、今回決めない範囲として簡潔に記載する。将来の担当 PR、ADR 番号、実装順序を予告しない。参照できる根拠だけでは判断できない事項は、確定事項として書かない。

基準コミットを持たない既存 ADR の説明を整理する場合は、「既存判断の記述整理」と明記して基準を補う。採用時の API 比較元は別に残し、整理時点のコードを当初の実装として説明しない。既存の基準コミットがある場合は維持する。

### 必須項目と読む順序

状態・日付・基準コミットをタイトル直後に置き、次のレベル 2 見出しをこの順で記載する。

| 見出し | 答えること |
| --- | --- |
| 背景 | 誰が、何をする際に、現在の何に困っているか。判断を制約する事実は何か |
| 決定 | 何をどう変えるか。なぜその方法を選ぶか |
| 検討した代替案 | 実際に比較した候補の利点と、今回は選ばない理由 |
| 結果と影響 | 利用者が得る効果、追加で負担する責務、互換性と制約 |

「背景」と「決定」の冒頭はそれぞれ一段落、目安は 2〜3 文とする。そこだけで問題・結論・利用者への変化を把握できるようにする。代替案がない場合はその理由を書き、比較していない案を水増ししない。

「決定」の中は、方針の要約、利用者の変更前・変更後、必要な契約、API 差分の順にする。未決定事項が主要な判断の成立を左右する間は「提案」とする。

### 利用者の変更前後を示す

- API・設定・操作手順を変更する ADR には、「利用者の変更前・変更後」を必ず置く。同じ利用者が同じ目的を達成する例を対にし、何を削除・追加・変更するかと、実行結果の違いを示す。
- コードの書き方が変わる場合は、変更前と変更後の呼び出しコードを示す。宣言の `diff` や「使いやすくなる」という説明だけで代用しない。設定や文書作成手順では、設定例・操作手順・短い対比表を使う。
- 変更前は基準コミットの実在する API・手順と照合する。変更後は今回の提案であることを明示し、宣言と契約に一致させる。コードの抜粋で省略した初期化や解放があれば、その範囲を示す。
- 新機能では、既存の代替手段または従来できなかったことと、新しくできることの最小例を示す。比較のために存在しない旧 API を作らない。
- 内部だけの変更なら、利用側の記述が変わらないことと、観測できる効果・制約を明記する。意味のない同一コードの対比は不要とする。
- 例は変更を理解できる最小範囲に絞る。ただし、判断に関わる所有権、失敗時の扱い、呼び出し順を省略して、実際より簡単に使えるように見せない。

### 文章と詳細の絞り方

一つの段落は一つの論点にし、利用者または処理の主体と動作を明記する。独自用語や略語は初出で短く説明し、説明用の英単語やスラッシュで名詞を連結しない。型名・メソッド名は正確な識別子を使用する。

採用する動作を先に述べる。誤用や互換性に関わる重要な制約は残すが、非目標、否定、注意書きを繰り返さない。同じ契約は一箇所に書き、他の箇所からはその節を参照する。

詳細は、採否の判断または利用方法を変える内容に限定する。所有権、状態遷移、スレッド・非同期、エラー、対応環境、移行など、関係する契約は省略しない。該当しない項目を機械的に埋めない。

一つの ADR は一つの主要な判断を扱う。独立して採否を決める必要がある判断は分割する。背景・理由・例で既に伝わる説明、実装手順、作業ログ、全 API の網羅的な解説は追加しない。短くするために必要な説明を別文書への参照へ押し出さない。

### 公開 API と契約の差分

公開境界を設計・変更する ADR には、判断対象の API と契約を必ず示す。公開 API と契約に影響しない場合は、その旨を明記して一覧を省略できる。

- 基準コミットとの比較を `diff` で示し、namespace、型、主要メンバーの C# 宣言を記載する。追加は `+`、削除は `-`、文脈は無印とする。改名では旧宣言の削除と新宣言の追加を両方示す。
- 基準コミットにある未実装の ADR の設計を変更する場合は、対象 ADR と節を比較元として明記し、実装との差分と混同しない。
- メンバー固有の役割、既定値、事前条件、失敗動作は宣言コメントに書く。共通の所有権や状態遷移は本文にまとめ、宣言から該当節を示す。シグネチャが同じでも、保証の変更はコメントの差分で示す。
- API・Desc・backend の内部契約を宣言する場合は同じ書式を使い、API 一覧を表形式にしない。状態遷移、所有権、対応環境、代替案には表を使用できる。
- 宣言は抜粋でよく、コンパイル可能な実装コードは要求しない。変更対象の削除・保証変更は省略しない。C ABI が判断対象の場合はその宣言も示す。

以下は、シグネチャを変えずに解放責任を変更する架空の書式例。実際の ADR では、基準コミットと対象コードを明記し、この差分より先に呼び出し側の変更例を置く。

```diff
 namespace Example
 {
     public sealed class Resource : IDisposable
     {
-        // 使用中は InvalidOperationException。複数回の解放を許容する。
+        // 呼び出し側が使用完了を保証する。使用中の検出は保証しない。複数回の解放を許容する。
         public void Dispose();
     }
 }
```

### 状態と検証

状態欄は次の 5 値のいずれか一つとし、括弧書きや実装進捗を付けない。

| 状態 | 意味 |
| --- | --- |
| 提案 | 検討中で、まだ合意していない |
| 採用 | 合意し、実装方針として使用する |
| 却下 | 検討したが採用しない |
| 廃止 | 適用を終了し、後継の判断がない |
| 置換済み | 有効な判断がすべて別の ADR に置き換わった |

設計に関わる実装は、対応する ADR を採用してから進める。合意済みの判断は最初から「採用」にできる。採用、main への取り込み、実装・検証の完了は別の事実である。主要な判断に合意済みと未合意の部分が混在する場合は、独立して採否を決められる単位に分ける。

ADR には判断の成立を確認する振る舞い、受け入れ条件、確認できない範囲を書く。実装進捗、実行ログ、レビュー対応は ADR 外で管理する。性能については期待する効果と保証を区別し、未測定の効果を実測値のように断定しない。測定レポートの比較履歴や数値の羅列を設計理由の代わりにしない。

### 変更と履歴

main に取り込む前は、採用済みでも同じ ADR を編集できる。結論を該当節へ統合し、代替案・例・影響も更新する。変更前の案を残すためだけに後継を作らない。取り込み前の統合・削除は可能とする。

main に取り込んだ後の設計変更は新しい ADR に記録する。事前条件、保証、失敗動作、所有権、依存方向を変える場合は、シグネチャが同じでも設計変更である。

| 種類 | 新しい記録 | 旧 ADR の扱い |
| --- | --- | --- |
| 全面置換 | 過去 ADR へのリンク、置き換える判断、理由を記載する | 後継の採用時に状態を「置換済み」へ変更する |
| 一部変更 | 過去 ADR へのリンク、対象の節・API・契約、理由、継続する範囲を記載する | 有効な判断が残る間は「採用」を維持する |
| 独立した追加 | 前提となる過去 ADR と、追加する判断を記載する | 既存判断を維持する |
| 意味を変えない補足 | 誤字・表記の修正と、基準コミットの記述で確認できる説明の明確化を同じ ADR に反映する | 状態・作成日・判断を維持する |

参照は新 ADR から過去 ADR への一方向とする。旧 ADR の冒頭には、変更日・理由・影響する範囲だけを管理情報として追記できる。後継の番号・リンクや新しい設計内容を遡って追加しない。提案中の判断で既存判断を失効させない。

旧 ADR の判断本文は上記の補足を除いて保持し、基準コミットを変えない。基準時点より後の事実や新しい判断を、補足の名目で追加しない。現在の変更関係は新 ADR の変更元から辿り、逆方向は参照元の検索で確認する。取り込み状況は main または origin/main の履歴で確認する。取り込み済み ADR は状態によらず削除せず、識別子・パス・作成日を変更しない。

### 配置と採番

ADR は日本語の Markdown で管理する。全体の運用・構成は直下、機能の判断は主たる責務のカテゴリに一度だけ配置する。

| 配置 | ファイル名 | タイトル |
| --- | --- | --- |
| `docs/adr/` | `NNNN-short-description.md` | `ADR-NNNN: 題名` |
| `docs/adr/<category>/` | `CATEGORY-NNNN-short-description.md` | `ADR-CATEGORY-NNNN: 題名` |

カテゴリ名と説明部分は英語の小文字・ハイフン、カテゴリコードはカテゴリ名の大文字表記とする。カテゴリは `src/` の責務を参考にするが一対一を要求しない。既存カテゴリと責務が重複するカテゴリを追加しない。

直下と各カテゴリは独立した採番範囲で、各 `0001` から開始する。同じ範囲の main、作業中の PR、番号予約を確認し、最大番号の次を割り当てる。並行作業では共通の管理場所で配置先・番号・担当を予約する。重複した場合は後から予約した側が取り込み前に修正し、関連参照も更新する。

番号は実装順や優先順位を表さない。予約済み・使用済みの番号は再利用せず、欠番を許容する。カテゴリを見直しても取り込み済み ADR の識別子とパスは維持する。

### 採用・更新時の必須確認

新規作成・採用・更新では、次を確認する。不整合が残る文書を完了扱いにしない。

- **読者**: 冒頭だけで誰の問題をどう解決するか分かる。利用側の変更前後または記述が変わらない旨があり、API 宣言だけで説明を済ませていない。
- **参照**: 基準 SHA と過去 ADR・ソースの存在を確認した。他の PR、将来の判断、作業経緯、許可していない資料への言及がない。
- **整合**: 決定、変更前後の例、API 差分、代替案、影響、検証方針が一致する。変更前は基準コードと、変更後は提案する契約と照合した。
- **簡潔さ**: 未説明の用語、重複、否定の羅列、判断に不要な内部詳細を除いた。必要な契約や利用者の責務まで削っていない。
- **構造と履歴**: 識別子の重複、ファイル名とタイトル、状態、日付、必須見出し、リンク先を検査した。変更元と範囲を示し、旧本文・識別子・作成日を保持した。

コードや API の確認は該当する場合だけ行う。Markdown lint と差分の空白検査に加えて内容を照合する。未変更の既存 ADR を一括で書き換えたり、形式だけを理由に採用済みの判断を未合意へ戻したりしない。新規・更新する記述に本規定を適用する。

Markdown lint の専用ルールで、識別子・メタデータ・必須見出し・利用例の位置・不許可な参照を検査する。導入時の既存 ADR は固定した本文ハッシュと一致する間だけ除外し、新規・編集した本文は検査する。検査を通すために除外ハッシュを更新しない。利用例の正しさ、採用理由、参照時点の意味、文章の分かりやすさは機械検査だけで判断せず、レビューで確認する。

### 記述テンプレート

直下の ADR はタイトルを `ADR-NNNN` にする。変更前後のコード・設定・手順は対象に合わせて記述する。

```markdown
# ADR-CATEGORY-NNNN: 利用者に起こる変化が分かる題名

- 状態: 提案
- 日付: YYYY-MM-DD
- 基準コミット: <固定 SHA>

## 背景

誰が何をするときに困るのか。基準コードと過去 ADR で確認した制約。

## 決定

何をどう変えるかと、採用する決め手。

### 利用者の変更前・変更後

同じ目的の変更前と変更後の最小例。必要な書き換えと結果の違い。
新規機能なら従来の代替手段と新しい使い方。内部変更なら記述不変と効果。

### 契約と API 差分

判断に必要な条件と変更対象の宣言。該当しなければ節を省略する。

## 検討した代替案

実際に比較した候補の利点と不採用理由。候補がない場合はその理由。

## 結果と影響

得られる効果、利用者の追加責務、互換性と制約。検証が必要な条件。
```

既存判断を変更する新 ADR では、メタデータに「変更関係」（全面置換または一部変更）、「変更元」（過去 ADR と対象節）、「変更対象」を追加する。一部変更では「継続する判断」も記載する。

## 検討した代替案

- API 一覧から説明する: 宣言を正確に示せるが、利用者が変更の目的と書き換え方を推測する必要がある。利用例の後に対象 API を示す。
- 作業経緯や外部文書を前提にする: 重複説明を省けるが、別の作業を追わないと判断を理解できない。過去 ADR と基準コードで問題を説明する。
- 全項目と実装進捗を必須にする: 形式的な記載漏れは減るが、不要な節と古くなる記録が増える。判断に関係する契約を選ぶ。
- 一部変更でも旧 ADR 全体を置換済みにする: 状態管理は単純になるが、残る契約も無効に見える。変更対象と継続範囲を新 ADR に示す。
- 全カテゴリ共通の連番にする: 番号だけで識別できるが、別カテゴリの並行作業にも調整が必要になる。カテゴリ内で独立して採番する。

## 結果と影響

読者は、利用者の問題と使い方の変化を先に把握し、必要な契約を順に確認できる。判断の根拠は基準コミットで再確認できる。

作成者は変更前の事実と利用例を照合し、作業経緯を除いて説明し直す必要がある。旧 ADR から後継への直接リンクは持たないため、現在の判断を調べる際は参照元を検索する。作成スキルは本 ADR を参照し、規則とテンプレートを重複管理しない。
