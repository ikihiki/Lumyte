# ADR の作成と更新

## 方針を確認する

1. リポジトリルートの `docs/adr/0001-adr-writing-policy.md` を読み、記述・状態・変更ルールに従う。このファイルが運用ルールの正本であり、以下の手順と差がある場合は ADR の規定を優先する。
2. `docs/adr/` の既存 ADR、対象の設計に関連する文書と実装、適用される `AGENTS.md` を確認する。
3. ユーザーが合意した方針、既存の設計判断、未決定事項を区別する。推測した方針を合意済みとして記録しない。

## 新規作成か更新かを選ぶ

- 新しい主要な設計判断は、新しい ADR に記録する。
- 提案中の ADR は検討内容に合わせて更新できる。
- ADR 自体が main に取り込まれるまでは、「採用」でも設計判断を含めて同じ ADR を編集する。取り込み前のレビューや実装中の見直しのために、後継 ADR を作らない。未取り込みの ADR の統合・削除と番号整理も可能とする。
- 誤字修正、説明の補足、採用済みのルールに沿った具体化は既存 ADR を更新する。例えば、既存のカテゴリ配置ルールに従うフォルダの追加は、構成図と役割表への追記で扱う。
- main に取り込まれた ADR の設計判断そのものを変える場合は、新しい ADR を作る。旧 ADR の状態を「置換済み」にし、変更日、理由、後継への相対リンクを追記する。新 ADR にも置換元への相対リンクを記載する。
- 「採用」と main への取り込みを区別し、main または origin/main の Git 履歴で取り込み状況を確認する。作業ツリーの未コミット状態だけで未取り込みと判断しない。
- main に取り込まれた ADR を削除したり、その番号を再利用したりしない。

## 内容を設計する

一つの ADR は一つの主要な判断を扱う。必須項目は、状態、日付、背景、決定、検討した代替案、結果と影響とする。

ADR-0001 の「設計対象に応じて選択する項目」から必要な内容を選ぶ。すべての項目を機械的に追加せず、判断を理解し、実装できるために必要な範囲を記述する。

特にライブラリの設計では、原則として対象範囲の公開 API 一覧を含める。

- 名前空間、公開型、主要なコンストラクター、メソッド、プロパティ、イベントを示す。
- 各 API のシグネチャ、役割、事前条件、失敗時の動作などの契約を記述する。
- 必要に応じて所有権、ライフサイクル、スレッド制約、非同期処理、短い利用例を示す。
- C# と C++ の境界では、C ABI、型対応、メモリとエラーの受け渡しを扱う。
- 既存ライブラリの変更では、追加・変更・廃止する API と関連する契約に絞ってよい。

複数環境に関わる設計では対応表を、依存方向や状態遷移の説明には必要に応じて図を使う。実装や測定が未実施なら、その結果を検証済みとして書かない。決められない事項は「別途決定する事項」に明示する。

## ファイルを作成する

- 配置先: `docs/adr/`。
- ファイル名: `NNNN-short-description.md`。既存番号の最大値に続く番号を使用し、説明部分は英語の小文字とハイフンにする。
- タイトル: `ADR-NNNN: 設計判断の題名`。
- 本文: 日本語。
- 日付: 作成日を `YYYY-MM-DD` で記録し、既存 ADR の作成日は保持する。
- 状態: 未合意なら「提案」。ユーザーとの会話やレビューで合意済みなら「採用」にできる。設計の採用と実装完了を区別する。

基本形は以下とし、選択した項目を「決定」の小見出し、または独立した節に追加する。

```markdown
# ADR-NNNN: 設計判断の題名

- 状態: 提案
- 日付: YYYY-MM-DD

## 背景

解決する問題、要求、制約。

## 決定

採用する方針と適用範囲。

## 検討した代替案

比較した選択肢と採用しなかった理由。

## 結果と影響

利点、欠点、制約、実装や運用への影響。
```

ADR 作成の依頼だけでは、実装プロジェクトや空フォルダを追加しない。関連 ADR を変更する場合は、依頼された判断に必要な範囲に限定し、既存のユーザー変更を保持する。

## 確認して報告する

- ファイル名とタイトルの番号、必須項目、状態、関連リンクの参照先を確認する。
- 公開 API と契約、依存関係、対応環境に矛盾がないか確認する。
- 更新した構成図や表に古い名前が残っていないか確認する。
- 新規ファイルを含む変更内容と Git の状態を確認し、不要な変更がないことを確かめる。文書のみの変更にはアプリのビルドやテストを追加しない。
- 作成・更新した ADR へのリンクと、主要な決定または未決定事項を簡潔に報告する。

## これまでの問題と対応

- ADR-0003 に具体的な導入パッケージや導入手順を書き込み、設計判断とセットアップの詳細を混在させた。開発環境の ADR には管理方針・責務・採用理由・制約・検証方針を記録し、具体的な導入内容は設定と手順書を参照する。
- ADR-0003 への指摘を、そのまま ADR-0001 の一般規定に追加した。個別 ADR 固有の指摘は対象の ADR に反映し、再発防止のための問題と対応はこのスキルに記録する。ADR-0001 の変更は共通の運用方針を変更する場合に行う。
