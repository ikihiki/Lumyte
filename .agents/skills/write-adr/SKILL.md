# ADR の作成と更新

## 方針を確認する

1. [ADR-0001: ADR の書き方と運用](../../../docs/adr/0001-adr-writing-policy.md) を読む。配置、採番、記述形式、状態、変更と履歴、必須確認はこの文書を正本とし、テンプレートも正本を使用する。
2. `docs/adr/` の既存 ADR、対象の設計に関連する文書と実装、適用される `AGENTS.md` を確認する。
3. 判断の前提とした main の commit SHA を固定し、その時点の過去 ADR とソースコードを確認する。ADR の状態と有効範囲も確認し、「過去」を番号の大小で判断しない。調査に使った会話、PR、外部資料などと、本文で参照できる根拠を分ける。
4. ユーザーが合意した方針と未決定事項を区別する。対象 ADR の main への取り込みは Git 履歴で確認し、未コミット状態だけで判断しない。確認できない事実を推測で「採用」や「実装済み」にしない。

## 新規作成か更新かを選ぶ

1. 今回の主要な判断と適用範囲を特定する。独立に採否が変わる判断は分ける。
2. 正本に従い、新規判断、取り込み前の編集、取り込み後の全面置換、一部変更、意味を変えない補足のいずれかを選ぶ。取り込み前の見直しは同じ ADR の該当箇所へ統合する。
3. 取り込み後の判断変更では、変更対象と継続する範囲を特定して後継 ADR を作る。参照は新 ADR から旧 ADR への一方向とする。旧 ADR の状態・変更日・理由は正本に従って更新し、後継の名前やリンクを追記しない。
4. 新規 ADR の配置、識別子、ファイル名は正本で決める。選んだ採番範囲の main、作業中の PR、番号予約を確認する。この作業情報は ADR 本文に持ち込まない。

## 内容を設計する

正本の必須項目とテンプレートを使い、次の順序で書く。選択項目を機械的に増やさない。

1. 誰が何に困り、何をどう変え、何が楽になり、どの負担が生じるかを冒頭で短く説明する。
2. API・設定・手順の変更には、同じ操作の Before／After 利用例を毎回示す。新規機能は初めてできることの最小例、内部だけの変更は呼び出し側の変更がないことを示す。宣言の `diff` だけで利用例を代用しない。
3. 方針、採用理由、代替案、影響、検証方針をつなげる。公開 API の `diff` は利用例の後に置き、判断対象に絞る。基準 commit からの改名・削除・契約だけの変更も示し、メンバー固有条件は宣言コメント、共通契約は本文にまとめる。
4. 短い文と一段落一論点で読み直す。日本語で意味が伝わる用語を選び、否定事項の列挙や作業経緯を除く。レビューの結論は該当箇所へ統合し、本文・利用例・差分をそろえる。
5. 状態は正本の五値、作成日は元の日付を保持する。本文の参照は基準時点の過去 ADR と固定 SHA のソースに限定する。PR・Issue・会話・将来予定・外部文書・実装進捗・測定ログは ADR 外で管理し、本文に案内リンクも置かない。

ADR 作成の依頼だけでは実装プロジェクトや空フォルダを追加しない。関連 ADR の変更は依頼された判断に必要な範囲に限定し、既存のユーザー変更を保持する。

## 確認して報告する

1. 正本の必須確認を適用する。冒頭と Before／After で利用者の変化が分かるか、本文、代替案、API 差分、影響、検証方針と矛盾しないかを確認する。
2. ADR 識別子の重複、ファイル名とタイトル、必須見出し、状態、参照先とアンカーを確認する。各参照が基準時点の範囲内にあること、作業文脈や後継への逆リンクが混入していないことも確認する。
3. リポジトリの文書チェックと差分の空白検査を実行し、新規ファイルを含む Git 差分を確認する。文書のみの変更ではアプリのビルドやテストを追加しない。
4. 作成・更新した ADR へのリンクと、利用者から見た主要な変更を Before／After とともに簡潔に報告する。未決定事項、確認結果、残る制約も伝える。

## これまでの問題と対応

- ADR-0003 に具体的な導入パッケージや導入手順を書き込み、設計判断とセットアップの詳細を混在させた。開発環境の ADR には管理方針・責務・採用理由・制約・検証方針を記録し、具体的な導入内容は設定と手順書で管理する。
- ADR-0003 への指摘を、そのまま ADR-0001 の一般規定に追加した。個別 ADR 固有の指摘は対象の ADR に反映し、再発防止のための問題と対応はこのスキルに記録する。ADR-0001 の変更は共通の運用方針を変更する場合に行う。
